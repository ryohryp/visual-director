# Visual Director v0.3 — Visual Asset Workflow & Management

## 1. Purpose

Visual Director v0.3 makes the game visual-production process visible and traceable from visual source of truth to generated asset.

v0.2 already resolves Visual Canon and Approved Visual Anchors into fail-closed Generation Packages. v0.3 keeps that foundation and adds the missing product layer: a UI and repository-backed workflow that lets a user see what the game should look like, what is being generated, what was generated, what is approved, and where the final asset lives.

The product goal is:

> Visual Director manages what should be created, what visual source of truth controls it, what was generated, what was approved, and where the approved asset is registered.

Visual Director is not itself the image-generation model. It directs and tracks the visual-production pipeline around one or more generators.

## 2. Product model

```text
Game Repository
  ├─ Visual Canon
  ├─ Grand Design / Global Visual Style
  ├─ Approved Visual Anchors
  └─ Existing Production Assets
          |
          v
Visual Director Core
          |
          v
Generation Package
          |
          v
Image Generator
          |
          v
Generated Result
          |
          v
Candidate
     ┌────┴────┐
     v         v
 Approved    Rejected
     |
     v
Registered Production Asset
```

The existing `VisualDirectorCore` remains the product core. MCP and the web UI are adapters around Core/API contracts and must not independently reinterpret Canon.

## 3. Source of truth

### 3.1 Repository first

Each game repository is the source of truth for project-specific visual state.

The repository owns:

- Visual Canon
- Grand Design / Global Visual Style references
- Approved Visual Anchors
- production/approved visual assets
- repository-managed workflow metadata introduced by v0.3

Visual Director must not introduce a second authoritative visual-asset store by default.

### 3.2 No mandatory Supabase or external storage

v0.3 does not require Supabase, a database, a vector store, or an external object-storage service.

Initial workflow state should be repository-backed. A logical structure may look like:

```text
.visual-director/
  jobs/
  candidates/
  rejected/
  asset-index.json

public/images/...   # approved / production assets
```

The exact metadata schema is an implementation detail and should remain small.

If repository size later becomes an actual operational problem, Git LFS or external object storage may be added as an optimization. It is not a prerequisite for v0.3.

## 4. Design principles

### Visual First

This is a visual-production tool. If an image exists, the UI should show the image rather than only its path or Markdown reference.

### Canon Alongside Image

A reference image without its controlling Canon is ambiguous. Important Canon constraints should be visible near Grand Design, Anchors, and generated assets.

### Repository First

Project state belongs to the game repository unless there is a demonstrated reason to externalize it.

### Canon First

The UI and generators must not silently reinterpret character identity, style, costume, or other Canon constraints.

### Fail Closed

Missing required Canon, missing required Approved Anchors, or inconsistent references must remain explicit failures. Legacy or Candidate assets must not silently become fallback sources.

### Human Approval

Generated output is never automatically promoted to Approved. Approval is an explicit user action.

### Generator Independent

Generation Package remains the contract between Visual Director and image generation. Visual Director should not become coupled to one image vendor.

### Minimal Architecture

Do not add a database, workflow engine, DAM platform, or generalized multi-provider framework before it is needed.

## 5. Visual sources of truth

The following become first-class visible objects in the v0.3 UI.

### 5.1 Grand Design / Project Visual Direction

A project dashboard should show the highest-level visual direction, including available representative imagery and the relevant Canon summary.

Examples of information that may be presented when the repository provides it:

- representative Grand Design image
- Global Visual Style reference
- art direction
- lighting direction
- environment/world direction
- forbidden visual direction

The UI must not invent missing design information.

### 5.2 Approved Visual Anchors

Approved Visual Anchors must be visually browsable.

The user should be able to see:

- Anchor image
- subject / category
- current Approved status
- repository path
- relevant Canon constraints
- generated assets that reference the Anchor
- superseded Anchor history where available

Character Anchors are only one category. The same concept can be used for locations, buildings, costumes, UI style, items, enemies, or other project-specific visual sources.

## 6. Asset lifecycle

Initial lifecycle:

```text
Requested
  -> Prepared
  -> Generating
  -> Generated
  -> Candidate
  -> Approved | Rejected
  -> Registered
  -> Superseded
```

### Requested

A user has requested a visual asset.

### Prepared

Core successfully resolved Canon and produced a valid Generation Package.

### Generating

A generator is processing the request.

### Generated

Generation completed and output exists.

### Candidate

The generated image is registered as a reviewable Visual Director asset.

### Approved

A user explicitly approved the Candidate.

### Rejected

A user explicitly rejected the Candidate. Rejection does not need to mean immediate deletion.

### Registered

An approved asset has been placed at its production repository path.

### Superseded

A newer approved asset replaced the previous one. History remains traceable.

## 7. Asset types

Visual Director must not be limited to character Anchors.

Initial conceptual asset types include:

- character visual anchor
- character full body
- character portrait
- character expression
- character sprite
- character costume
- background
- location visual
- event CG
- item
- icon
- UI asset
- enemy / monster
- map
- building
- effect
- other

Project-specific asset types may be supported without changing the overall product model.

## 8. Web UI

### 8.1 Projects

List configured projects and high-level visual workflow state.

Useful summary values include:

- assets
- Candidates
- review items
- failed jobs

### 8.2 Project Dashboard

The dashboard should answer at a glance:

- What does this game currently look like?
- What are the current Approved Anchors?
- What is being generated now?
- What was generated recently?

The top of the dashboard should prioritize visual direction rather than operational metadata.

### 8.3 Visual Overview

Display available Grand Design and Global Visual Style imagery prominently.

Example structure:

```text
Project

VISUAL DIRECTION
[ Grand Design / Global Visual Reference ]

CHARACTERS
[ Anchor ] [ Anchor ] [ Anchor ]

LOCATIONS / OTHER ANCHORS
[ Anchor ] [ Anchor ]

RECENT GENERATIONS
[ Asset ] Candidate
[ Asset ] Approved
[ Asset ] Failed
```

### 8.4 Anchor Gallery

Display Approved Anchors as image cards grouped/filterable by category or subject.

### 8.5 Anchor Detail

Show:

- large Anchor preview
- current/superseded state
- subject/category
- repository path
- relevant Canon constraints
- related generated assets

### 8.6 Generation Jobs

Display generation activity with at least:

- Job ID
- project
- subject
- asset type
- request
- status
- generator
- created/updated timestamps when available
- result count
- explicit error state

### 8.7 Asset Gallery

Generated assets must be visible as thumbnails.

Required status distinctions:

- Candidate
- Approved
- Rejected
- Registered
- Superseded

Useful filters:

- project
- subject
- asset type
- status

### 8.8 Asset Detail

Show:

- image preview
- lifecycle status
- subject
- asset type
- source Generation Job
- generator
- Generation Package fingerprint when available
- reference assets
- relevant Canon constraints
- Candidate path / production repository path

## 9. Visual lineage

A key differentiator from a generic image gallery is that Visual Director shows why a generated image exists and what controlled it.

Conceptual lineage:

```text
Grand Design / Global Visual Style
          |
          v
Approved Visual Anchor
          |
          v
Generation Package
          |
          v
Generated Candidate
          |
          v
Approved / Registered Asset
```

A generated asset should be traceable back to the specific references used for that generation. Relationships must come from stored/reference metadata; the UI must not infer unsupported relationships.

When an Anchor is replaced, assets created from the previous Anchor remain associated with that Anchor generation.

## 10. Generation Job metadata

A minimal Generation Job model should be sufficient to reconstruct the generation context without introducing a workflow platform.

Conceptual shape:

```json
{
  "job_id": "gen_0142",
  "project_id": "bottom-of-thirst",
  "asset_type": "character_full_body",
  "subject_ids": ["kamino_kyosuke"],
  "request_text": "Generate a full-body visual for Kamino Kyosuke",
  "status": "candidate",
  "generation_package_fingerprint": "...",
  "generator": "...",
  "created_at": "...",
  "updated_at": "..."
}
```

Whether the complete Generation Package snapshot is persisted or reconstructed from a content-addressed snapshot should be decided during implementation. The requirement is traceability: the user must be able to determine what constraints and references produced an asset.

## 11. Asset metadata

Conceptual Candidate metadata:

```json
{
  "asset_id": "asset_0281",
  "project_id": "bottom-of-thirst",
  "subject_id": "kamino_kyosuke",
  "asset_type": "character_full_body",
  "status": "candidate",
  "source_job_id": "gen_0142",
  "generator": "...",
  "generation_package_fingerprint": "...",
  "candidate_path": "...",
  "registered_path": null,
  "created_at": "...",
  "approved_at": null,
  "supersedes": null
}
```

This is a design example, not a frozen schema.

## 12. Candidate and production storage

Generated output should not be placed directly into production paths.

Candidate output belongs to a repository-managed working area first. Approved output is later registered at the project production path.

This separation keeps the production tree clean while preserving review history.

Ordinary Git is acceptable for the initial implementation. Git LFS or external object storage should only be introduced when measured repository growth justifies it.

## 13. MCP and API

MCP remains one adapter into Visual Director, not the application core.

The target architecture is:

```text
Web UI ----┐
           v
          API/Core
           ^
MCP -------┘
```

Potential future operations include preparing generation, listing visual state, registering Candidates, and reviewing assets. Exact MCP tool names are not part of this design baseline.

## 14. Delivery phases

### Phase 1 — Make the workflow visible

Highest priority.

Deliver:

- repository visual/workflow read model
- web UI shell
- Project Dashboard
- Grand Design / Global Visual Style visualization
- Approved Anchor Gallery and Detail
- Generation Job visualization
- Asset Gallery and Asset Detail
- visual lineage display

Phase 1 should be useful even before Visual Director can initiate image generation itself.

### Phase 2 — Candidate review lifecycle

After visibility is established:

- Candidate registration
- Approve
- Reject
- production registration
- Superseded history

Hosted write access requires a separate security review because the current hosted backend is intentionally read-only.

### Phase 3 — Generator integration

Only after the visible workflow and review model are usable:

- one initial generator path
- generating/succeeded/failed job status
- successful output automatically becomes Candidate
- no automatic approval

Do not build a generalized multi-provider framework until a second provider actually requires it.

## 15. Non-goals for v0.3

- full Digital Asset Management platform
- Photoshop-like image editing
- video generation
- 3D asset management
- independent image model hosting
- vector database
- generalized workflow engine
- automatic AI approval
- complex organization/user permission management

## 16. v0.3 success criteria

When a user opens a project in Visual Director, they can answer without manually browsing repository files:

1. What is the current visual direction of this game?
2. What are the current Approved Anchors?
3. What is being generated now?
4. What was generated recently?
5. Which images are Candidate, Approved, Rejected, Registered, or Superseded?
6. What Canon / Grand Design / Anchor controlled a generated image?
7. Where does an approved production asset live in the game repository?

The most important outcome is that image generation becomes a visible, traceable production process instead of a hidden sequence of tool calls.
