# Visual Director v0.4 — Multi Project Workspace

## 1. Purpose

Visual Director v0.4 adds first-class multi-project management on top of the v0.3 visual-production workflow.

v0.3 made one game project's visual direction, Approved Anchors, generation jobs, Candidates, and registered assets visible and traceable. v0.4 makes Visual Director itself a workspace that can manage multiple game projects without mixing their visual state.

The product goal is:

> Visual Director is a multi-project visual-production workspace. Each game remains isolated by project, while each game repository remains the source of truth for its own Canon, Anchors, generation history, Candidates, and production assets.

The top-level user flow becomes:

```text
Visual Director
  -> Projects
      -> Game Project
          -> Visual Direction
          -> Anchors
          -> Generations
          -> Assets
```

## 2. Design principles

### Project Isolation

Visual state from one game must never appear as if it belongs to another game.

Every Core/API/UI operation that reads or mutates project-specific state must be resolved from an explicit `project_id`.

### Repository First

The game repository remains authoritative for project-specific visual state.

Visual Director may keep a small Project Catalog that tells it where a project repository is and which adapter/configuration applies. The catalog must not duplicate Canon, Anchor, Candidate, Generation Job, or production asset state.

### No Project-Specific Environment Variable Sprawl

Do not add one deployment environment variable per project such as:

```text
VISUAL_DIRECTOR_GAME_A_GITHUB_REPO
VISUAL_DIRECTOR_GAME_B_GITHUB_REPO
VISUAL_DIRECTOR_GAME_C_GITHUB_REPO
```

Project repository configuration should be resolved through a catalog/configuration model.

Secrets such as GitHub credentials may remain deployment configuration, but project identity and repository mapping should not be encoded as an ever-growing set of environment variable names.

### Explicit Adapter Selection

Visual Director must not assume that every game has exactly the same Canon layout.

A Project Catalog entry can specify an adapter type. The initial design should support a specific project adapter and a generic/default adapter without introducing a plugin framework.

## 3. Project Catalog

Visual Director maintains a small catalog of configured projects.

Conceptual shape:

```json
{
  "projects": [
    {
      "project_id": "bottom-of-thirst",
      "display_name": "The Bottom of Thirst",
      "repository": "ryohryp/---The-Bottom-of-Thirst",
      "ref": "main",
      "adapter_type": "bottom-of-thirst"
    },
    {
      "project_id": "game-b",
      "display_name": "Game B",
      "repository": "ryohryp/game-b",
      "ref": "main",
      "adapter_type": "generic"
    }
  ]
}
```

This is a conceptual contract, not a frozen persistence schema.

The catalog owns only workspace-level routing/configuration:

- `project_id`
- display name
- repository identity
- default ref/branch
- adapter type
- optional project-level presentation metadata

It does not own:

- Visual Canon
- Grand Design
- Global Visual Style
- Approved Anchors
- Generation Jobs
- Candidates
- Rejected assets
- Registered production assets

Those remain in the game repository.

## 4. Project identity

`project_id` is the stable Visual Director identifier for a game project.

Requirements:

- unique within one Visual Director workspace
- URL-safe
- stable even if repository display name changes
- never inferred from the current UI page alone when calling Core/API
- included or resolved explicitly for all project-scoped operations

Repository name and `project_id` do not need to be identical.

## 5. Workspace UI

### 5.1 Projects Home

`/` becomes the Projects workspace instead of opening a single game's dashboard directly.

The page shows one card per configured game.

Example:

```text
Visual Director

PROJECTS

┌──────────────────────────────┐
│ The Bottom of Thirst         │
│                              │
│ [Visual direction thumbnail] │
│                              │
│ Anchors       7              │
│ Candidates    3              │
│ Jobs         12              │
│ Failed        0              │
│                              │
│ Open Project ->              │
└──────────────────────────────┘

┌──────────────────────────────┐
│ New Game                     │
│                              │
│ Connect Repository ->        │
└──────────────────────────────┘
```

A project card should preferentially use the project's explicit Grand Design image, then Global Visual Style reference, as its visual thumbnail. If neither exists, show a clear placeholder rather than inventing imagery.

### 5.2 Project Dashboard

Selecting a project opens the existing visual-production dashboard scoped to that game only.

The dashboard keeps the v0.3 sections:

- Visual Direction
- Grand Design / Global Visual Style
- Approved Anchors
- Workflow summary
- Recent Generation Jobs

### 5.3 Project Navigation

Each project exposes project-scoped navigation for at least:

```text
Overview
Anchors
Generations
Assets
```

The currently selected project must remain visible in navigation so users cannot accidentally confuse assets from different games.

## 6. URL model

Preferred route structure:

```text
/
  Projects workspace

/projects/:project_id
  Project dashboard

/projects/:project_id/anchors
  Approved Anchor gallery

/projects/:project_id/anchors/:subject_id
  Anchor detail

/projects/:project_id/generations
  Generation Jobs

/projects/:project_id/assets
  Asset Gallery

/projects/:project_id/assets/:asset_id
  Asset detail where a dedicated route is useful
```

The exact rendering mechanism may remain server-rendered HTML in the current minimal implementation. A frontend framework is not required merely to support these routes.

Legacy routes such as `/assets` or `/anchor` may temporarily redirect to the configured default project during migration, but the new canonical URLs must include `project_id`.

## 7. API model

Project-scoped API calls must carry project identity explicitly.

Preferred route style:

```text
/api/projects
/api/projects/:project_id/overview
/api/projects/:project_id/assets
/api/projects/:project_id/asset
```

Query-parameter forms can remain temporarily for backward compatibility, but the Core contract must never depend on one hard-coded project.

The API must fail explicitly when:

- `project_id` is unknown
- project configuration is invalid
- repository cannot be accessed
- required project Canon is missing

It must not silently substitute another project or a default repository.

## 8. Core and registry model

The target resolution flow is:

```text
project_id
   |
   v
Project Catalog
   |
   +--> repository config
   |
   +--> adapter_type
            |
            v
       Project Adapter
            |
            v
    VisualDirectorCore
```

`VisualDirectorCore` remains independent from web routes and MCP transport.

Project-specific logic should be selected by catalog/registry resolution rather than `if project_id === "bottom-of-thirst"` checks spread throughout Core or HTTP handlers.

A small registry switch is acceptable. A generalized plugin system is not required.

## 9. Adapter model

Initial conceptual adapter types:

```text
bottom-of-thirst
  project-specific Canon interpretation where required

generic
  shared/default Canon conventions
```

Adapters may define:

- Canon document locations
- Approved Anchor extraction rules
- project-specific visual overview resolution
- optional project-specific validation

Adapters must not redefine workspace routing or store project state outside the game repository.

## 10. Project setup flow

Adding a game should be a repository connection workflow, not a manual environment-variable exercise.

Conceptual flow:

```text
Connect Repository
      |
      v
Project configuration
      |
      v
Repository diagnostics
      |
      v
Project added to workspace
```

Initial setup fields may include:

- project id
- display name
- GitHub repository
- ref/branch
- adapter type

## 11. Repository diagnostics

Before treating a project as ready, Visual Director should diagnose what visual sources exist.

Example:

```text
Project Setup Diagnostics

✓ Repository accessible
✓ Visual Canon found
✓ Global Visual Style found
✓ Approved Anchor definitions found
○ Grand Design not configured
○ Workflow index not created yet
```

Diagnostic states should distinguish:

- ready/present
- optional/not configured
- required/missing
- access/error

Missing optional data such as Grand Design or workflow index should not be fabricated.

Missing required Canon must remain fail-closed for operations that need it.

## 12. Project card summary model

The Projects Home may show a small read model aggregated from each repository:

```json
{
  "project_id": "bottom-of-thirst",
  "display_name": "The Bottom of Thirst",
  "thumbnail": "docs/visual/assets/global_visual_style_reference.webp",
  "anchors": 7,
  "candidates": 3,
  "jobs": 12,
  "failed_jobs": 0,
  "repository_status": "ready"
}
```

Counts are derived from repository-backed project state; Visual Director should not maintain a second authoritative count store.

For initial implementation, loading summaries directly from repositories is acceptable. Caching should only be introduced if performance becomes a measured problem.

## 13. Generation and asset isolation

Generation Jobs and managed assets are always project-scoped.

A job identifier only needs to be unique within its project unless implementation convenience makes global uniqueness cheap.

The effective identity of an asset is conceptually:

```text
(project_id, asset_id)
```

The UI must never merge Asset Galleries from different games by default.

A future global search across projects may exist, but it must display project identity prominently and is not required for v0.4.

## 14. Repository-backed workflow remains unchanged

Within each game repository, the v0.3 repository-first model remains valid:

```text
.visual-director/
  candidates/
  superseded/
  asset-index.json

public/images/...
```

Each project's `.visual-director/asset-index.json` describes only that game's jobs and managed assets.

No central workflow database is introduced by v0.4.

## 15. Hosted configuration

Hosted Visual Director may use one read credential capable of accessing configured repositories only where that is operationally acceptable, or repository-scoped credentials/installations when stronger isolation is required.

Project Catalog entries must never contain raw credentials.

The catalog may contain repository identifiers, but authentication remains deployment/security configuration.

The hosted write boundary defined separately for repository mutations continues to apply independently per configured project.

## 16. Migration from current single-project UI

Current implementation assumes `bottom-of-thirst` in several routes and runtime paths.

Migration should proceed incrementally:

1. introduce Project Catalog and project summary contract
2. make Core/HTTP project resolution catalog-backed
3. change `/` to Projects Home
4. move existing Dashboard under `/projects/:project_id`
5. move Anchor / Generation / Asset pages under project-scoped routes
6. retain temporary redirects for old routes if useful
7. remove hard-coded `bottom-of-thirst` routing/configuration branches where catalog/adapter resolution can replace them
8. add a second fixture/project to prove isolation

Do not rewrite the current UI or Core architecture merely for route cleanup.

## 17. v0.4 non-goals

- central DAM database
- organization/team workspaces
- role-based access control
- cross-project asset sharing
- automatic Canon migration between games
- project templates marketplace
- generalized plugin framework
- project-wide vector search
- mandatory Git LFS/object storage

## 18. Acceptance criteria

v0.4 is successful when:

1. Visual Director opens to a Projects list rather than one hard-coded game.
2. Two or more configured game projects can coexist.
3. Selecting one game shows only that game's visual direction, Anchors, Jobs, and Assets.
4. Project URLs include `project_id`.
5. Project repository mapping is resolved from a Project Catalog rather than one environment-variable name per game.
6. Existing Repository First behavior remains unchanged inside each game repository.
7. A new repository can be diagnosed for Visual Director readiness.
8. Missing optional Grand Design/workflow data is shown explicitly rather than inferred.
9. Unknown project IDs fail closed.
10. Automated tests prove that data from project A cannot appear when project B is requested.

## 19. Recommended implementation slices

Implement v0.4 in small slices:

### Slice 1 — Project Catalog and read model

- project configuration type
- list projects
- project summary
- catalog-backed repository/adapter resolution

### Slice 2 — Project-scoped routing

- Projects Home
- `/projects/:project_id`
- project-scoped Anchor / Generation / Asset routes
- legacy route migration

### Slice 3 — Repository setup diagnostics

- validate repository access
- detect required/optional Canon resources
- show readiness state

### Slice 4 — Multi-project isolation tests

- at least two project fixtures
- Core/API/UI resolution tests
- no cross-project fallback

A database, frontend framework, or generalized plugin system is not required for any of these slices.

## 20. Relationship to v0.3

This document extends, rather than replaces, `docs/v0.3-visual-asset-workflow.md`.

v0.3 defines the visual-production lifecycle within one project.

v0.4 defines how multiple such projects coexist in one Visual Director workspace.
